# 橋を渡れ！

崩れやすい吊り橋を、みんなで同時に渡るパーティゲーム。急ぐと板が割れる。慎重すぎると時間切れ。
リンクを送るだけで、スマホのブラウザから参加できる。

- 人数: 1〜100人（1人でも試せる）
- 1回: 35〜60秒（人数で変わる）＋秒読み3秒
- 手元のポート: 8105

## 遊び方

1. ニックネームを入れて「部屋を作る」。出てきた招待URL（/r/コード）か4文字の参加コードを送る
2. ホストが「スタート」。3秒の秒読みのあと、全員が同時に橋を渡り始める
3. 画面を**ドラッグ**すると歩く（指を置いた所がスティックの中心）。「**走る**」を押している間は速く走れる
4. 「待って」「行け」「危ない」の合図で周りに声をかけられる（頭の上に吹き出しが出る）
5. 時間内に**全員の7割**が向こう岸に着けば**チーム成功**。個人は着順（着けなかった人は進んだ距離）で順位がつく

PC: 矢印キー / WASD で移動、Shift か Space で走る、1・2・3 で合図。

## ルール

| 要素 | 中身 |
|---|---|
| 橋 | 幅は人数で変わる（3人まで3列、100人で18列）。長さ28段。7段ごとに支柱があり、そこで区間が分かれる |
| 板の耐久 | 1枚ずつ耐久がある。乗っているだけで少しずつ減る。最初から傷んでいる板（ひびの絵）が約14% |
| 重さの上限（板） | 1枚に重さ2.5まで。歩く人は1、走る人は2。上限を超えると急に傷む（3人で乗ると約3秒で割れる） |
| 重さの上限（区間） | 区間ごとに「列数×1.3」まで。超えると、その区間の**全部の板**が傷む（橋が揺れて「ゆれ」「重すぎ」と出る） |
| 走る | 速さ1.8倍。ただし重さ2倍＋足元の板を揺らして傷める |
| 突風 | 5〜8秒ごとに、ある区間に予告（黄色の点線、1.5秒）→ 吹く（2秒）。吹いている区間で動いている人は重さ3倍。止まっていれば普段どおり |
| 落ちる | 割れた板の上にいると落ちる。2.5秒後にスタートの崖へ戻る（何度でも挑戦できる） |
| 橋が落ちる | どこかの段が全部割れると橋が落ち、乗っていた人は全員落ちて終わり |
| 終わり | 時間切れ・全員ゴール・橋が落ちた、のどれか |
| 賞 | 一番乗り / 橋にやさしい（ゴールした人で板を傷めた量が一番少ない）/ 破壊王（板1枚ぶん以上傷めた人の中で一番） |

色だけに頼らない: 傷んだ板はひびの線の数、重すぎる板は「!」、区間は「ゆれ」「重すぎ」の札、突風は文字の帯で出す。

## 大人数対応（負荷試験）

### やったこと

雛形の送り方は「毎 tick（20回/秒）、人ごとに全状態を作って JSON にして送る」。100人だと 1 tick で 100回の view と JSON 化が走り、
1回の中身も100人分あるので、送る量は人数の2乗で増える。これを次のように変えた。

1. **ゲーム中は差分だけを送る**（`t:'f'`）。動いた人と、耐久の段階が変わった板だけ。2秒に1回だけ全員分をまとめて送る（取りこぼしの保険）
2. **全員に同じ中身は1回だけ JSON にして使い回す**。このゲームには秘密が無いので、差分は Buffer を1つ作って全員に送る。部屋の全体の状態（ロビーや結果）も、共通部分を1回だけ JSON にして人ごとには `you` だけ足す（`meta.sharedView`）
3. **位置は 0.1 単位の整数**、状態は番号、板の耐久は 0〜10 の段階にして短いキーで送る（`p:[番号,x,y,状態,...]`）
4. **物理は20回/秒、配るのは10回/秒**。画面側は2つの差分の間を補間し、自分だけは押した瞬間に動いて見せる（サーバーの位置へ少しずつ寄せる）
5. 画面側の入力は「変わったときだけ・最大15回/秒」

比較のため、雛形と同じ送り方も `BRIDGE_NAIVE=1`（`node tools/load.mjs --naive`）で残してある。

### 測り方

- `tools/load.mjs` がサーバーを別プロセス（`STATS=1` で `/stats` を開く）で起動し、ws クライアントを N 本つないで1部屋で遊ばせる
- ボットは 150ms ごとにランダムな向き（前寄り）へ動き、3割は走る（1人あたり約6.7回/秒の操作。人の操作より多め）。2%の確率で合図も送る
- 各20秒。ゲームが終わったら即再戦して、測る間はずっとゲーム中にする（「再戦」列が回数）
- サーバー: 送信量（ws に渡したバイト数）、tick の所要時間（ゲームを進める＋送るまで）、CPU（process.cpuUsage）、メモリ（RSS の最大）
- クライアント: 1秒ごとの ping の往復時間、1人あたりの受信量、差分が届く間隔
- 環境: この Mac（Apple M5、10コア、16GB、Node v26.4.0、**電池駆動**）の localhost。サーバーとボットは別プロセスだが同じマシン（2026-10-26 測定）

改善後は 100人でも tick が 50ms の枠の 1% 未満、CPU 3% で、この Mac では余裕がある。

### まだ残っているボトルネック（数字）

- **送信量は今も人数の2乗で増える**: 1回の差分は「動いている人数」に比例し（100人が全員動くと約 0.9 KB）、それを全員に送るため。10→30→50→100人で 15→92→239→888 KB/s。
  100人で約 7 Mbps。1部屋100人なら問題ない量だが、100人部屋を同時にいくつも開くと、CPU より先に回線の上限が来る
- 次に効く手（未実施）: 差分をバイナリ（1人5バイト程度）にする → 約半分 / 自分から遠い人は5回/秒に落とす / 画面に入っていない人を送らない（ただし右端の全体図で全員を出しているので、仕様と相談）

### この数字の限界

- localhost なので回線の遅延・帯域・パケットロスは入っていない。ping 往復 1〜2ms は「サーバーの処理待ちが小さい」ことを示すだけで、実際のスマホ回線の遅れ（数十〜数百ms）は別に乗る
- 本番サーバー（Render の無料プラン等）はこの Mac より CPU が遅く、帯域や同時接続にも上限がある。同じ数字にはならない（未確認）
- ボットは画面を描かない。**100人を描くスマホ側の重さ（fps）は実機で測っていない**（headless の chromium / webkit で表示と操作が通ることだけ確認）
- 実際の人間10人での同時プレイはしていない。10人は ws ボット（load.mjs）と、ブラウザ1台＋ボット9人（layout.mjs）、ブラウザ3台（e2e.mjs）で確かめた

## デプロイ

1フォルダ＝1サービス。どれも契約が要るので、まだ公開していない。

- Render: render.yaml をそのまま Blueprint に使う（`healthCheckPath: /healthz`）
- Fly.io / Cloud Run 等: Dockerfile（node:22-alpine、PORT=8080）
- og:image は index.html を返すときに、来たホスト名（`x-forwarded-host` / `host`）で絶対URLに書き換える。プロキシが `x-forwarded-proto: https` を付ける前提（各サービスで付くかは未確認。付かないと http の URL になる）
- `/stats` は環境変数 `STATS=1` のときだけ開く（本番では付けない）

## 今後の改善点

- 差分のバイナリ化と、遠い人の更新を間引く（上の「まだ残っているボトルネック」）
- 突風の頻度・板の耐久・時間は、実際に遊んだ感触で調整が要る（ボットのシミュレーションでは「全員で一斉に走ると100人なら10秒前後で橋が落ちる」「時間差で出ると成功する」まで確認）
- 落ちた人に「次に誰を行かせるか」を指示させるなど、ゴール後・落下後の人の役割
- 100人のときは自分の色が他人と同じになる（12色を使い回している）。自分だけは白い輪と「あなた」で区別している
